# Project Commit Message Generator

프로젝트의 Git 커밋 메시지를 팀 컨벤션에 맞게 자동으로 생성하는 스킬입니다.

## 필수 실행 규칙 (반드시 준수)

1. **`git add .`를 가장 먼저 실행한다** - 어떤 작업보다 먼저, 무조건 `git add .`를 실행하여 모든 변경사항을 스테이징한다.
2. **커밋 메시지 생성 후 확인 없이 즉시 커밋한다** - 사용자에게 "이 메시지로 커밋할까요?" 같은 질문을 절대 하지 않는다. 메시지를 생성하면 바로 `git commit`을 실행한다.

## 팀 커밋 컨벤션

우리 팀은 다음 규칙을 따릅니다:

### 형식
```
<타입>: <제목>

<본문>
```

### 규칙
1. **타입**: feat, fix, docs, refactor, chore, test, style, perf 중 하나
2. **제목**: 80자 이내, 한국어, 마침표 없음
3. **본문**: 불릿 포인트(-) 형식, 변경 이유와 내용 설명

### 예시
```
feat: 사용자 인증 미들웨어 추가

- JWT 토큰 검증 구현
- 역할 기반 접근 제어 추가
- 인증 에러 핸들링 생성
```

## 사용 방법

### 1. 자동 생성 (권장)

Git에서 파일을 stage한 후 스크립트 실행:

```bash
# 파일 stage
git add .

# 커밋 메시지 생성 (대화형)
python scripts/commit_generator.py
```

**실행 과정:**
1. `git add .` 실행 (모든 변경사항 자동 스테이징)
2. staged 변경사항 분석
3. 커밋 메시지 자동 생성
4. 확인 없이 즉시 커밋 실행

### 2. 옵션

#### 자동 커밋 (편집 없이)
```bash
python scripts/commit_generator.py --auto
```

사용자 확인 없이 바로 커밋합니다.

#### Dry Run (메시지만 생성)
```bash
python scripts/commit_generator.py --dry-run
```

커밋하지 않고 메시지만 생성하여 확인합니다.

#### 다른 저장소 지정
```bash
python scripts/commit_generator.py --repo /path/to/repo
```

현재 디렉토리가 아닌 다른 저장소의 커밋 메시지를 생성합니다.

### 3. Claude를 통한 사용

사용자가 요청하면 Claude가 자동으로:

1. **`git add .` 실행 (필수, 가장 먼저)**
   - 모든 변경사항을 자동으로 스테이징
   - 이 단계는 항상 제일 먼저 실행됨

2. **staged 변경사항 분석**
   ```bash
   git diff --staged
   ```

3. **변경사항 이해**
   - 추가/수정/삭제된 파일
   - 파일 타입 (코드, 문서, 설정)
   - 주요 변경 내용

4. **적절한 타입 선택**
   - 새 파일 추가 → `feat`
   - 버그 수정 → `fix`
   - 문서만 변경 → `docs`
   - 코드 개선 → `refactor`
   - 설정 변경 → `chore`

5. **커밋 메시지 생성**
   - 80자 이내의 명확한 제목
   - 주요 변경사항을 불릿 포인트로 나열

6. **확인 없이 즉시 커밋 실행**
   - 사용자에게 수정 여부를 묻지 않고 바로 커밋

## 커밋 타입 가이드

### feat (새로운 기능)
새로운 기능을 추가할 때

**예시:**
```
feat: 장바구니 수량 조절 기능 추가

- 수량 증가/감소 버튼 추가
- 최소/최대 수량 제한 구현
- 실시간 가격 계산 연동
```

**사용 시기:**
- ✅ 새 API 엔드포인트
- ✅ 새 UI 컴포넌트
- ✅ 새 기능 모듈
- ❌ 기존 기능 수정

### fix (버그 수정)
버그를 수정할 때

**예시:**
```
fix: 로그인 시 세션 만료 오류 수정

- 토큰 갱신 로직 개선
- 만료 시간 계산 오류 수정
- 에러 핸들링 추가
```

**사용 시기:**
- ✅ 크래시 수정
- ✅ 예외 처리
- ✅ 잘못된 로직 수정
- ❌ 코드 품질 개선

### docs (문서 변경)
문서만 변경할 때

**예시:**
```
docs: API 사용 가이드 추가

- RESTful API 엔드포인트 문서화
- 요청/응답 예시 추가
- 인증 방법 설명 추가
```

**사용 시기:**
- ✅ README 수정
- ✅ 주석 추가
- ✅ 문서 파일 변경
- ❌ 코드와 함께 변경

### refactor (리팩토링)
기능 변경 없이 코드 구조 개선

**예시:**
```
refactor: 사용자 서비스 계층 분리

- 비즈니스 로직을 서비스로 이동
- 컨트롤러 코드 간소화
- 의존성 주입 구조 개선
```

**사용 시기:**
- ✅ 코드 구조 개선
- ✅ 중복 코드 제거
- ✅ 변수명 개선
- ❌ 버그 수정
- ❌ 새 기능 추가

### chore (설정 변경)
빌드, 설정, 의존성 변경

**예시:**
```
chore: 프로덕션 환경 설정 추가

- 환경 변수 설정 파일 추가
- 빌드 스크립트 업데이트
- 의존성 버전 업데이트
```

**사용 시기:**
- ✅ package.json 수정
- ✅ 빌드 설정 변경
- ✅ CI/CD 설정
- ✅ .gitignore 수정

## 작동 원리

### 1. 변경사항 분석

스크립트는 `git diff --staged`를 실행하여:

- **파일 변경 통계**
  - 추가된 파일 수
  - 수정된 파일 수
  - 삭제된 파일 수
  - 추가/삭제된 라인 수

- **파일 타입 분류**
  - 코드 파일 (.py, .js, .dart 등)
  - 문서 파일 (.md, .txt)
  - 설정 파일 (package.json, pubspec.yaml)
  - 테스트 파일 (*test*, *spec*)
  - 스타일 파일 (.css, .scss)

- **주요 변경 내용 추출**
  - 새로운 함수/클래스 정의
  - 새로운 import 문
  - 파일 추가/삭제

### 2. 커밋 타입 선택

변경사항을 기반으로 가장 적절한 타입을 제안:

| 조건 | 제안 타입 |
|------|-----------|
| 문서 파일만 변경 | docs |
| 테스트 파일만 변경 | test |
| 설정 파일만 변경 (1-2개) | chore |
| 스타일 파일만 변경 | style |
| 새 파일 추가 + 많은 추가 라인 | feat |
| 많은 삭제 라인 | fix 또는 refactor |
| 여러 파일 수정 | refactor |
| 기본값 | feat |

### 3. 메시지 생성

#### 제목 생성
- 주요 변경사항 중 첫 번째 항목 사용
- 또는 파일 변경 통계로 일반적 설명 생성
- 80자 초과 시 자동으로 잘라내기

#### 본문 생성
- 주요 변경사항을 불릿 포인트로 나열
- 파일 통계 추가 (파일 수, 라인 수)
- 최대 5개 항목으로 제한

### 4. 대화형 편집

생성된 메시지를 보여주고 자동으로 커밋 까지 실행:

```
생성된 커밋 메시지:
============================================================
feat: 사용자 프로필 편집 기능 추가

- 프로필 이미지 업로드 구현
- 닉네임 변경 기능 추가
- 2개 파일 추가
- +120 -10 라인
============================================================
```

## 상세 가이드 참조

더 자세한 커밋 컨벤션은 `references/commit_convention.md` 참조:

- **각 타입별 상세 설명**: 언제 사용하고 언제 사용하지 말아야 하는지
- **좋은 예시 vs 나쁜 예시**: 실제 사례 비교
- **특수한 경우**: Breaking changes, hotfix 등
- **커밋 주기와 크기**: 언제, 어떻게 커밋해야 하는지
- **팀 규칙**: 필수사항, 권장사항, 금지사항

## 베스트 프랙티스

### 1. 커밋 전 체크리스트
- [ ] 코드가 빌드되고 실행되는가?
- [ ] 테스트가 통과하는가?
- [ ] 하나의 논리적 변경만 포함하는가?
- [ ] 불필요한 파일이 포함되지 않았는가?

### 2. 좋은 커밋 습관
- ✅ 작은 단위로 자주 커밋
- ✅ 의미 있는 커밋 메시지 작성
- ✅ 기능별로 커밋 분리
- ✅ 테스트 통과 후 커밋

### 3. 피해야 할 습관
- ❌ "WIP", "temp" 같은 임시 커밋
- ❌ 동작하지 않는 코드 커밋
- ❌ 여러 기능을 한 커밋에 포함
- ❌ 타입 없이 커밋

## 문제 해결

### "No staged changes found"
**원인:** stage된 파일이 없습니다.

**해결:**
```bash
git add .
```

### "Failed to get staged changes"
**원인:** Git 저장소가 아니거나 Git이 설치되지 않았습니다.

**해결:**
1. Git이 설치되어 있는지 확인: `git --version`
2. 현재 디렉토리가 Git 저장소인지 확인: `git status`
3. 아니라면 초기화: `git init`

### 생성된 메시지가 부적절함
**원인:** 변경사항이 복잡하거나 자동 분석의 한계

**해결:**
1. 옵션 "2" 또는 "3"을 선택하여 수동 수정
2. 또는 스크립트 사용 없이 직접 작성
3. 커밋을 더 작은 단위로 분리 고려

## 통합

### Git Hooks
`.git/hooks/prepare-commit-msg`에 추가하여 자동화:

```bash
#!/bin/bash
python scripts/commit_generator.py --auto
```

### IDE 통합
- VS Code: 터미널에서 스크립트 실행
- IntelliJ: External Tools로 등록
- Vim: 커맨드로 등록

### CI/CD
커밋 메시지 검증을 CI에 추가:

```yaml
# .github/workflows/commit-lint.yml
name: Commit Lint
on: [push, pull_request]
jobs:
  lint:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v2
      - name: Check commit message
        run: |
          # 커밋 메시지 형식 검증
          git log -1 --pretty=%B | grep -E "^(feat|fix|docs|refactor|chore|test|style|perf):"
```
