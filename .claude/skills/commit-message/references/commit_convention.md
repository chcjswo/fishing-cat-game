# 팀 커밋 컨벤션 가이드

이 문서는 프로젝트의 Git 커밋 메시지 작성 규칙을 정의합니다.

## 기본 원칙

### 1. 명확성 (Clarity)
- 커밋 메시지만 읽어도 무엇이 변경되었는지 이해할 수 있어야 합니다
- 구체적인 변경 내용을 포함합니다

### 2. 일관성 (Consistency)
- 팀의 정해진 형식을 따릅니다
- 같은 타입의 변경은 같은 prefix를 사용합니다

### 3. 간결성 (Conciseness)
- 제목은 80자 이내로 작성합니다
- 불필요한 세부사항은 생략합니다

## 커밋 메시지 구조

```
<타입>: <제목>

<본문>
```

### 제목 (Title)
- **길이**: 80자 이내
- **언어**: 한국어
- **형식**: `타입: 제목`
- **끝**: 마침표 없음

### 본문 (Body)
- **언어**: 한국어
- **형식**: 불릿 포인트 (-)로 시작
- **내용**: 
  - 무엇을 변경했는지
  - 왜 변경했는지 (필요시)
  - 어떤 영향이 있는지 (필요시)

## 커밋 타입 (Types)

### feat (새로운 기능)
새로운 기능을 추가할 때 사용합니다.

**예시:**
```
feat: 사용자 프로필 편집 기능 추가

- 프로필 이미지 업로드 구현
- 닉네임 변경 기능 추가
- 자기소개 편집 UI 생성
```

**사용 시기:**
- ✅ 새로운 API 엔드포인트 추가
- ✅ 새로운 UI 컴포넌트 추가
- ✅ 새로운 기능 모듈 구현
- ❌ 기존 기능 수정 (→ refactor 또는 fix)

### fix (버그 수정)
버그를 수정할 때 사용합니다.

**예시:**
```
fix: 로그인 시 세션 만료 오류 수정

- 토큰 갱신 로직 개선
- 만료 시간 계산 오류 수정
- 에러 핸들링 추가
```

**사용 시기:**
- ✅ 크래시 수정
- ✅ 예외 처리 개선
- ✅ 잘못된 로직 수정
- ✅ UI 버그 수정
- ❌ 코드 품질 개선 (→ refactor)

### docs (문서 변경)
문서만 변경할 때 사용합니다.

**예시:**
```
docs: API 사용 가이드 추가

- RESTful API 엔드포인트 문서화
- 요청/응답 예시 추가
- 인증 방법 설명 추가
```

**사용 시기:**
- ✅ README 수정
- ✅ 주석 추가/수정
- ✅ 문서 파일 (.md, .txt) 변경
- ❌ 코드와 함께 변경 (→ 주 변경사항의 타입 사용)

### refactor (리팩토링)
코드 구조를 개선하되 기능은 변경하지 않을 때 사용합니다.

**예시:**
```
refactor: 사용자 서비스 계층 분리

- 비즈니스 로직을 서비스로 이동
- 컨트롤러 코드 간소화
- 의존성 주입 구조 개선
```

**사용 시기:**
- ✅ 코드 구조 개선
- ✅ 중복 코드 제거
- ✅ 함수/클래스 분리
- ✅ 변수명 개선
- ❌ 버그 수정 (→ fix)
- ❌ 새 기능 추가 (→ feat)

### chore (설정 변경)
빌드, 설정, 의존성 관련 변경을 할 때 사용합니다.

**예시:**
```
chore: 프로덕션 환경 설정 추가

- 환경 변수 설정 파일 추가
- 빌드 스크립트 업데이트
- 의존성 버전 업데이트
```

**사용 시기:**
- ✅ package.json, pubspec.yaml 등 의존성 파일 수정
- ✅ 빌드 설정 변경
- ✅ CI/CD 설정 변경
- ✅ .gitignore 수정
- ❌ 코드 로직 변경 (→ 다른 타입 사용)

### test (테스트 추가/수정)
테스트 코드를 추가하거나 수정할 때 사용합니다.

**예시:**
```
test: 사용자 인증 유닛 테스트 추가

- 로그인 성공/실패 케이스 테스트
- 토큰 갱신 테스트
- 권한 검증 테스트
```

**사용 시기:**
- ✅ 새로운 테스트 추가
- ✅ 기존 테스트 수정
- ✅ 테스트 구조 개선
- ❌ 프로덕션 코드와 함께 변경 (→ 주 변경사항의 타입 사용)

### style (코드 스타일 변경)
코드의 의미에 영향을 주지 않는 형식적 변경을 할 때 사용합니다.

**예시:**
```
style: 코드 포맷팅 적용

- Prettier 설정 적용
- 들여쓰기 통일
- 불필요한 공백 제거
```

**사용 시기:**
- ✅ 포맷팅 변경
- ✅ 세미콜론 추가/제거
- ✅ 공백, 줄바꿈 정리
- ❌ 코드 로직 변경 (→ 다른 타입 사용)

### perf (성능 개선)
성능을 개선하는 코드 변경을 할 때 사용합니다.

**예시:**
```
perf: 이미지 로딩 성능 개선

- 레이지 로딩 구현
- 이미지 캐싱 추가
- 썸네일 생성 최적화
```

**사용 시기:**
- ✅ 알고리즘 최적화
- ✅ 데이터베이스 쿼리 최적화
- ✅ 캐싱 추가
- ✅ 불필요한 연산 제거

## 좋은 커밋 메시지 vs 나쁜 커밋 메시지

### ✅ 좋은 예시

```
feat: 장바구니 수량 조절 기능 추가

- 수량 증가/감소 버튼 추가
- 최소/최대 수량 제한 구현
- 실시간 가격 계산 연동
```

**좋은 이유:**
- 명확한 타입 (feat)
- 구체적인 제목
- 상세한 변경 내용
- 80자 이내

### ❌ 나쁜 예시

**예시 1: 불명확한 제목**
```
feat: 업데이트

- 코드 수정
```

**문제점:**
- 무엇을 업데이트했는지 불명확
- "코드 수정"은 너무 일반적

**개선안:**
```
feat: 장바구니 기능 추가

- 상품 추가/삭제 구현
- 수량 조절 기능 추가
```

**예시 2: 타입 불일치**
```
fix: 새로운 검색 필터 추가

- 카테고리별 필터 구현
- 가격 범위 필터 추가
```

**문제점:**
- 새로운 기능인데 fix를 사용
- 올바른 타입은 feat

**개선안:**
```
feat: 검색 필터 기능 추가

- 카테고리별 필터 구현
- 가격 범위 필터 추가
```

**예시 3: 제목이 너무 김**
```
feat: 사용자가 자신의 프로필 페이지에서 닉네임, 이메일, 프로필 이미지를 수정할 수 있는 편집 기능을 추가하고 변경 사항을 실시간으로 저장하는 기능 구현
```

**문제점:**
- 제목이 80자를 훨씬 초과
- 너무 많은 정보를 담으려고 함

**개선안:**
```
feat: 프로필 편집 기능 추가

- 닉네임, 이메일 수정 구현
- 프로필 이미지 변경 기능
- 실시간 저장 기능 추가
```

## 특수한 경우

### 여러 타입이 섞인 경우
가장 중요한 변경사항의 타입을 사용하거나, 커밋을 분리합니다.

**분리 권장:**
```
# 커밋 1
feat: 로그인 API 연동

# 커밋 2
docs: 로그인 API 사용법 문서화
```

### 긴급 수정 (Hotfix)
긴급한 버그 수정의 경우에도 fix 타입을 사용합니다.

```
fix: 결제 실패 긴급 수정

- 결제 API 타임아웃 처리 추가
- 에러 메시지 개선
```

### Breaking Changes
API나 기능이 크게 변경되어 하위 호환성이 깨지는 경우:

```
feat!: 인증 시스템 v2로 전환

- JWT에서 OAuth 2.0으로 변경
- 기존 토큰 형식 지원 중단
- 마이그레이션 가이드 참조 필요

BREAKING CHANGE: 기존 인증 토큰이 더 이상 작동하지 않습니다.
```

## 커밋 주기

### 언제 커밋할까?

✅ **커밋하기 좋은 시점:**
- 하나의 논리적 변경이 완료되었을 때
- 테스트가 통과할 때
- 코드가 동작하는 상태일 때
- 기능 단위 작업이 끝났을 때

❌ **커밋하지 말아야 할 때:**
- 코드가 빌드되지 않을 때
- 테스트가 실패할 때
- 작업이 반만 완료되었을 때
- 여러 기능이 뒤섞여 있을 때

### 커밋 크기

- **작은 커밋 (Small)**: 권장 ✅
  - 리뷰하기 쉬움
  - 문제 발생 시 롤백하기 쉬움
  - 히스토리 추적이 명확

- **큰 커밋 (Large)**: 지양 ❌
  - 리뷰 어려움
  - 문제 발생 시 원인 파악 어려움
  - 히스토리가 불명확

## 자동화 도구 사용

### commit_generator.py 사용법

```bash
# 기본 사용 (대화형)
python scripts/commit_generator.py

# 자동 커밋 (편집 없이)
python scripts/commit_generator.py --auto

# 메시지만 생성 (커밋 안함)
python scripts/commit_generator.py --dry-run

# 다른 저장소 지정
python scripts/commit_generator.py --repo /path/to/repo
```

### 작동 방식

1. `git diff --staged` 실행
2. 변경사항 분석
   - 추가/수정/삭제된 파일
   - 파일 타입 (코드, 문서, 설정 등)
   - 코드 변경 패턴
3. 적절한 커밋 타입 제안
4. 커밋 메시지 자동 생성
5. 사용자 확인 및 수정
6. 커밋 실행

### 생성 예시

**입력 (staged changes):**
```diff
+++ b/lib/services/auth_service.dart
+ class AuthService {
+   Future<User> login(String email, String password) async {
+     // Implementation
+   }
+ }
```

**출력 (generated message):**
```
feat: 인증 서비스 추가

- AuthService 클래스 구현
- 로그인 메서드 추가
- 1개 파일 추가
- +50 라인
```

## 팀 규칙

### 필수 사항
1. ✅ 모든 커밋은 정해진 타입을 사용해야 함
2. ✅ 제목은 80자를 초과할 수 없음
3. ✅ 한국어로 작성해야 함
4. ✅ 본문은 불릿 포인트 형식 사용

### 권장 사항
1. 💡 하나의 커밋은 하나의 목적만 가질 것
2. 💡 커밋 전에 반드시 테스트할 것
3. 💡 의미 있는 단위로 커밋할 것
4. 💡 자동 생성 도구를 활용할 것

### 금지 사항
1. ❌ "WIP", "temp", "test" 같은 임시 커밋 메시지
2. ❌ 타입 없이 커밋하지 말 것
3. ❌ 동작하지 않는 코드를 커밋하지 말 것
4. ❌ 한 커밋에 여러 기능을 섞지 말 것
